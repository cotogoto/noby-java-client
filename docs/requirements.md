# 要件定義（現行実装ベース）

## 1. 文書の位置づけ

この文書は、`noby-java-client` リポジトリで確認できる実装、設定、READMEを根拠に、現行仕様を整理したものである。NOBY API本体や、このライブラリを利用するアプリケーションの仕様は対象外であり、確認できない内容は推測せず「未確認事項」とする。

## 2. システムの目的

JavaアプリケーションからNOBY APIへ会話文と設定値を送信し、会話結果・感情解析・固有表現等をJavaオブジェクトとして取得するクライアントライブラリを提供する。

## 3. 対象ユーザー

- Maven/JitPack経由で本ライブラリを利用するJava開発者
- NOBY APIのアプリケーションキーを保有するアプリケーション開発者

エンドユーザー向け画面やユーザー管理機能は、このリポジトリには存在しない。

## 4. 主な利用シナリオ

1. 利用側がアプリケーションキーと任意の `Setting` を用意する。
2. `NobyClient` を生成する。
3. `exec(String message)` に会話文を渡す。
4. 外部NOBY APIの応答を `Result` として受け取る。
5. HTTPエラー、APIエラー、通信・デコードエラーは例外として利用側が処理する。

## 5. 機能要件

### 5.1 クライアント生成

- `NobyClient(String appKey, Setting setting)` で生成する。
- `setting` は `null` を許容する。
- `appKey` の `null` は生成時ではなく `exec` 実行時に拒否される。
- 空文字のアプリケーションキーは現行実装では拒否されない。

### 5.2 会話API実行

- `exec(String message)` はNOBY APIへHTTP GETを送る。
- 必須クエリは `app_key` と `text` である。
- `text` はUTF-8でURLエンコードする。
- 任意クエリは `mail`、`pass`、`token`、`lat`、`lng`、`study`、`persona`、`ending` である。
- HTTP 200の場合、JSON内に `errors` がなければ `Result` へデコードする。
- JSON内に `errors` があれば、先頭から走査した最初のエラーメッセージを例外として送出する。

### 5.3 結果モデル

`Result` は、会話結果、コマンド、ムード、ネガポジ、感情、単語解析、人工物名・組織名・人名・地名・日付・時刻表現を保持する。詳細な項目は [api-spec.md](api-spec.md) を参照する。

## 6. 非機能要件（確認済み範囲）

- Javaソース／ターゲットバージョン: 11（`pom.xml` とEclipse設定）
- ビルド: Maven、成果物形式はJAR
- 文字コード: `text` の送信時はUTF-8。Mavenのプロジェクトエンコーディングは未指定で、ビルド環境依存の警告が出る。
- スレッド安全性: `Parameters` は `CopyOnWriteArrayList` を使うが、`NobyClient` 全体の並行利用可否は明記もテストもない。
- タイムアウト、再試行、サーキットブレーカー、レート制限対応は実装されていない。
- ログ基盤はなく、ライブラリ本体はログを出力しない。
- `jakarta.ws.rs.client.Client` のクローズ処理は実装されていない。

## 7. 入力・出力

### 入力

- アプリケーションキー: `String`、実質必須（`null` のみ検証）
- 会話文: `String`。必須とJavaDocに記載されるが、`null`／空文字の明示検証はない。
- `Setting`: 全項目任意

### 出力

- 正常時: `ai.cotogoto.noby.model.Result`
- 異常時: 宣言上は `Exception`。アプリケーションキーが `null` の場合は `NullPointerException`。

## 8. 権限・認証

- 本リポジトリ内に認証・認可機構はない。
- 外部API向けに `app_key` を送る。さらに任意で `mail` と `pass`、または `token` を送信できる。
- これらはURLクエリとして送信されるため、利用側および中継機器のアクセスログへの記録に注意する。
- 認証項目の組み合わせ、優先順位、有効期限、必要権限は外部API仕様で要確認。

## 9. 正常系・異常系・境界値

### 正常系

- 有効な `appKey`、会話文、任意設定を送信し、HTTP 200のJSONを `Result` に変換する。
- `Setting` が `null` または全項目 `null` の場合、必須項目のみ送信する。

### 異常系

- `appKey == null`: `NullPointerException`
- HTTPステータスが200以外: 本文を読まず `Exception("HTTP error: <status>")`
- HTTP 200かつ `errors` を含むJSON: APIのエラーメッセージを `Exception` で送出
- 通信、URL構築、レスポンス読取、JSON変換の失敗: 下位ライブラリ由来の例外が伝播

### 境界値・未検証入力

- 空の `appKey`、空または `null` の `message`
- 非常に長い会話文（GET URL長制限）
- `study` と `persona` の定義外整数
- 緯度・経度の範囲外、`NaN`、無限大
- `ending` や任意文字列に予約文字を含む場合（`text` 以外はURLエンコードされない）
- HTTP 200だが空、不正、または想定外構造のJSON

## 10. 今回確認できた既存仕様

- 実装対象はJavaクライアントライブラリのみで、Controller、Service、Repository、Entity、DTO、View、画面、DBはない。
- 外部接続先はソースに固定された `https://app.cotogoto.ai/webapi/noby.json` である。
- READMEの利用例は現行のコンストラクタと `exec` に整合する。
- POMのプロジェクトバージョンは `0.7.2-SNAPSHOT`、SCMタグ設定は `v0.7.1` である。
- READMEの更新履歴に記載された最新は `0.7.0` であり、POMおよびGitタグと一致しない。

## 11. 未確認事項・要確認事項

- NOBY APIの現行公式仕様、必須／任意条件、文字数・値域、レスポンススキーマ、エラーコード
- `mail`/`pass` と `token` を同時指定した場合の扱い
- APIの可用性、タイムアウト、レート制限、SLA、サポート対象TLS
- 取得した会話・位置・認証データの外部API側での保存、個人情報・学習利用方針
- ライブラリのサポート対象Javaランタイムと依存関係更新方針
- JitPackで公開される正式な最新バージョンとリリース手順

## 12. NOBY APIエラーに関する変更要求

### 12.1 背景

利用側システム `god` のAlexa連携において、Alexaから「今日の天気は」という入力を受けた後、`NobyClient.exec()` がNOBY APIからHTTP 400を受け、例外が利用側の上位処理へ伝播した事象が報告されている。その結果、`/god/alexa` がHTTP 500を返し、Alexa側では `INVALID_RESPONSE` と判定されてセッションが終了した。

報告された処理の流れは次のとおりである。

1. Alexaが利用側システムへ発話内容を送信する。
2. 利用側の `InputAnyHandler` が `NobyClient.exec()` を実行する。
3. NOBY APIがHTTP 400を返す。
4. NOBYクライアントからの例外が利用側の上位処理へ伝播する。
5. 利用側のAlexaエンドポイントがHTTP 500を返す。
6. Alexaが応答を無効と判定してセッションを終了する。

同時期に、利用側の `VoiceServlet` が生成されていないMP3ファイルを参照し、ファイル不存在となった事象も報告されている。ただし、`InputAnyHandler`、`VoiceServlet`、`/god/alexa`、Alexaレスポンス生成、MP3生成は本リポジトリには存在しないため、実装上の因果関係はこのリポジトリだけでは確認できない。

### 12.2 目的

- NOBY APIが要求を拒否した場合に、原因調査に必要な情報を、秘密情報や個人情報を漏えいさせず取得できるようにする。
- NOBY APIの障害が、利用側システムで未処理のHTTP 500や無効なAlexa応答へ直結しないようにする。
- 音声生成に失敗した場合、存在しない音声ファイルを後続処理が参照しないようにする。

### 12.3 対象範囲

#### 本リポジトリの対象

- `NobyClient.exec()` が受信するHTTPエラーの識別可能性
- NOBY APIのエラー応答から、利用側が安全に障害を判定するために必要な情報
- 既存の公開Java APIおよび例外動作との互換性

#### 利用側システムで対応すべき範囲

- `InputAnyHandler` におけるNOBY API失敗時の例外処理
- Alexaが受理できるフォールバック応答の生成
- HTTP 500を避けるためのエンドポイント全体のエラー処理
- MP3生成完了およびファイル存在の確認
- 音声ファイルが利用できない場合の代替応答

利用側システムの要求は関連要求として記録するが、本リポジトリで直接実装する対象には含めない。

### 12.4 機能要件

#### REQ-ERR-001 HTTPエラーの判定

- NOBY APIがHTTP 200以外を返した場合、呼び出し元がHTTPエラーであることとステータスコードを判定できること。
- HTTP 400と、認証、権限、レート制限、サーバー障害等の他ステータスを呼び出し元が区別できること。
- ステータスごとの業務上の意味や再試行可否は、公式NOBY API仕様を確認するまで確定しない。

#### REQ-ERR-002 エラー詳細の取得

- NOBY APIがエラーレスポンス本文を返す場合、原因調査に必要な範囲で内容を確認できること。
- エラー本文が空、不正JSON、未知の形式、または過大なサイズでも、エラー処理自体が新たな未処理例外の原因にならないこと。
- エラー本文を例外、戻り値、ログのいずれで提供するかは設計時に決定する。

#### REQ-ERR-003 機密情報の保護

- `app_key`、`mail`、`pass`、`token` をエラー情報やログへ平文で出力しないこと。
- 会話文、緯度、経度、API応答に含まれる個人情報・機微情報を無制限に記録しないこと。
- 完全な要求URLをログへ出力しないこと。
- 記録対象、マスキング、長さ制限、保存期間は運用主体が確認すること。

#### REQ-ERR-004 利用側でのフォールバック

- 利用側システムは、NOBY API呼び出しの失敗を捕捉し、Alexaが有効と判定できる応答を返すこと。
- フォールバック応答では、ユーザーに一時的に回答を取得できない旨を通知できること。
- セッションを終了するか継続するか、具体的な文言、再試行を案内するかはプロダクト要件として別途確認すること。
- NOBY APIの失敗だけを理由に、利用側のAlexaエンドポイントが未処理のHTTP 500を返さないこと。

#### REQ-ERR-005 音声ファイルの参照

- 利用側システムは、音声ファイルをAlexa応答または取得用URLへ設定する前に、生成が正常終了して利用可能であることを確認すること。
- 音声ファイルが存在しない、生成途中、読取不能、または期限切れの場合、存在しないファイルのURLを返さないこと。
- 音声ファイルを利用できない場合、Alexa標準の音声応答等へ切り替えられること。具体方式は利用側システムで決定する。

### 12.5 非機能要件

- 診断性: HTTPステータス、外部APIエラーの発生時刻、呼び出し単位を関連付けて調査できること。ただし秘密値を識別子に使用しない。
- 可用性: 外部NOBY APIの単一要求失敗によって、利用側プロセスや後続リクエストの処理が継続不能にならないこと。
- セキュリティ: エラー診断の追加によって認証情報・個人情報の露出範囲を拡大しないこと。
- 互換性: 本ライブラリの公開APIまたは例外契約を変更する場合、既存利用側への影響を評価し、移行方法を定めること。
- 性能: 本事象を処理速度の問題とは確定しない。タイムアウト要件は別途、外部APIのSLAとAlexa側の応答期限を確認して定めること。

### 12.6 入力・出力

#### 入力

- HTTP 400を含むNOBY APIからの非200レスポンス
- 本文がJSON、非JSON、空、または未知形式であるエラーレスポンス
- 利用側から渡される会話文および認証・任意設定

#### 出力

- 本ライブラリ: `NobyHttpException` によるHTTPステータス、最大8,192文字のレスポンス本文、および本文切詰め有無
- 利用側システム: Alexaが有効と判定できるフォールバック応答
- 音声生成失敗時: 存在しないMP3 URLを含まない応答

Alexa側のJSON構造および文言は本リポジトリの範囲外であり、未確定である。

### 12.7 正常系・異常系・境界値

#### 正常系

- NOBY APIがHTTP 200の正常JSONを返す場合、従来どおり `Result` を取得できること。
- 音声生成を利用する場合、生成済みかつ読取可能なファイルのみ参照されること。

#### 異常系

- HTTP 400とエラー本文あり／なし
- HTTP 401、403、404、429、500系
- 接続拒否、DNS、TLS、接続・読取タイムアウト
- HTTP 200だがAPIエラーを表す本文
- 空、不正、未知形式、非常に大きいエラー本文
- 利用側のフォールバック応答生成自体の失敗
- MP3生成失敗、ファイル不存在、読取不能、削除済み

#### 境界値

- `null`、空文字、予約文字、非ASCII、長文の会話入力
- 空または定義外の認証・任意パラメータ
- ログやエラー情報へ保持可能な本文の最大長
- 音声生成完了と参照開始が競合するタイミング

### 12.8 受入条件

- NOBY APIがHTTP 400を返した試験で、利用側がステータスを識別できる。
- 原因調査に必要なエラー情報を確認でき、秘密値と完全な要求URLは出力されない。
- 同じ試験で、利用側のAlexaエンドポイントが未処理例外によるHTTP 500を返さない。
- Alexaへ返す応答が対象プラットフォームの有効なレスポンス仕様を満たす。
- MP3が生成されない試験で、存在しないファイルのURLを応答へ含めない。
- NOBY APIが正常な場合、既存の正常応答が維持される。

本リポジトリ内で確認できる受入条件は、本ライブラリに関係する項目までである。AlexaおよびMP3に関する条件は `god` 側のリポジトリで検証する必要がある。

### 12.9 未確認事項・要確認事項

- 障害発生時にNOBY APIへ送信された実際のパラメータ構成。ただし秘密値そのものは収集・共有しない。
- HTTP 400で返された実際のレスポンス本文とContent-Type
- NOBY APIの現行エラー仕様、再試行可能なステータス、レスポンス本文の機密性
- `god` 側の例外処理、Alexaレスポンス生成、音声生成、ファイル公開の現行実装
- Alexaの応答期限、フォールバック応答仕様、セッション終了方針
- MP3不存在がNOBY API失敗から派生したものか、独立した競合・保存期間・パス問題か
- エラー本文をログへ記録できる運用・セキュリティ上の可否
- 利用側が新しい専用例外を直接利用するか、従来どおり `Exception` として扱うか

### 12.10 実装時に確定した事項

- HTTPエラーは `Exception` の派生型 `NobyHttpException` で通知する。
- `NobyClient.exec(String)` の引数、戻り値、`throws Exception` は維持する。
- 例外メッセージは従来どおり `HTTP error: <status>` とする。
- HTTPステータスは `getStatus()`、本文は `getResponseBody()` で取得する。
- 本文は8,192文字まで保持し、超過時は切り詰め、`isResponseBodyTruncated()` で判定できる。
- nullまたは取得不能な本文は空文字として扱う。本文取得時の原因例外は `getCause()` で確認できる。
- 本文、完全な要求URL、認証情報を例外メッセージへ含めず、ライブラリからログ出力しない。
- HTTP 200の正常応答とAPI `errors` 応答の既存動作は維持する。

これらは本ライブラリ内の実装事項である。利用側のフォールバック応答、MP3存在確認、ログ運用は引き続き未実装・未確認である。
