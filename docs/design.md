# 設計書（現行実装ベース）

## 1. 全体アーキテクチャ

本リポジトリは単一MavenモジュールのJavaクライアントライブラリである。Webサーバー、画面、永続化層は持たない。

```text
利用側Javaアプリケーション
  └─ NobyClient
      ├─ Parameters（クエリ文字列組み立て）
      ├─ Jakarta REST/Jersey Client（HTTPS GET）
      ├─ JSONIC（JSONデコード）
      └─ model（Setting / Result / Emotion / Negaposi / Word）
             │
             └── https://app.cotogoto.ai/webapi/noby.json
```

## 2. 主要コンポーネントと責務

| 種別 | クラス | 責務 |
|---|---|---|
| クライアント | `ai.cotogoto.noby.NobyClient` | 設定保持、必須値検証、HTTP要求、HTTP/APIエラー判定、結果変換 |
| ヘルパー | `ai.cotogoto.noby.Parameters` | 名前と値を保持し、`name=value&...` 形式へ連結 |
| 入力モデル | `ai.cotogoto.noby.model.Setting` | 認証、位置、学習、人格、語尾の任意設定 |
| 出力モデル | `ai.cotogoto.noby.model.Result` | 会話および解析結果のルートモデル |
| 出力モデル | `Emotion` | 単語ごとの感情値 |
| 出力モデル | `Negaposi` | 単語ごとのネガポジ値 |
| 出力モデル | `Word` | 形態・単語解析結果 |

Lombok `@Data` がモデルのgetter/setter、`equals`、`hashCode`、`toString` 等を生成する。

## 3. レイヤー別の有無

- Controller: なし
- Service: 専用層なし。外部通信と変換を `NobyClient` が担当
- Repository / Entity: なし。DBを使用しない
- DTO: DTOという命名はないが、`Setting` と結果モデル群が境界データを表す
- View / Component / Template: なし

## 4. データの流れ

1. 利用側が `appKey` と `Setting` をコンストラクタへ渡す。
2. `NobyClient` は `Setting` の値を自身のフィールドへコピーする。
3. `exec(message)` が `appKey` の `null` を検証する。
4. `Parameters` に `app_key` とURLエンコード済み `text` を追加する。
5. 非 `null` の任意設定を追加し、クエリ文字列へ連結する。
6. 固定URLへ `Accept: application/json` のGET要求を送る。
7. HTTP 200以外ならステータスのみの例外を投げる。
8. HTTP 200なら本文を文字列で読み、文字列に `errors` が含まれるか判定する。
9. エラー応答はJSONをMap/Listへデコードし、メッセージを例外化する。正常応答は `Result` へデコードする。

## 5. 外部連携

- 接続先: `https://app.cotogoto.ai/webapi/noby.json`
- 方式: HTTPS GET
- HTTPクライアント: Jersey 3.1.2
- JSON変換: JSONIC 1.3.10
- URLはコードに固定され、環境変数や設定ファイルによる切替はない。
- 接続・読取タイムアウト、プロキシ、再試行は明示設定されていない。

## 6. エラー処理

- `appKey == null`: `NullPointerException`
- HTTP 200以外: レスポンス本文を読まず、汎用 `Exception` にステータスのみ含める。
- APIエラー: HTTP 200本文に文字列 `errors` が含まれた場合に、構造をMap/Listとして解釈して汎用 `Exception` を投げる。
- その他: Jersey、JSONIC、JDK由来例外がそのまま上位へ伝播する。

現行実装には独自例外型、エラーコード、レスポンス本文の保存、フォールバック、リトライはない。利用側は `exec` の例外を必ず処理する必要がある。

## 7. ログ方針

ライブラリ本体にロガーはない。テスト用 `main` のみ `System.out.println(result)` を使用する。認証情報・会話文・位置情報を含み得るため、ログを追加する場合は以下を守る。

- `app_key`、`mail`、`pass`、`token`、完全な要求URLをログに出さない。
- エラー本文を記録する場合も、認証情報・個人情報のマスキングと長さ制限を行う。
- ライブラリ側でロギング実装を固定する変更は、互換性と依存追加を人間が判断する。

## 8. 既存設計上の注意点

- `text` だけを事前エンコードし、他の文字列値はエンコードしない。`Parameters` 自体はURLエンコードを行わない。
- GETクエリに認証情報と本文を含めるため、URLログ・URL長の影響を受ける。
- `json.contains("errors")` はJSON構造ではなく文字列で分岐する。
- HTTPエラー本文を読まないため、400等の原因をライブラリ利用側で特定できない。
- `Client` はクライアント生成ごとに作られ、明示的にクローズされない。
- `Result` の数値プリミティブは、項目欠落時と値0を区別できない。
- 外部URLを差し替えられないため、モックサーバーを使った単体・結合テストが難しい。
- `commons-io` は現行ソースから利用されていない。

## 9. 変更時に守るべき設計方針

- 公開コンストラクタ、`exec`、モデルのプロパティは利用側との互換性を持つ公開APIとして扱う。
- 外部API仕様を確認せず、パラメータ名、値域、JSONフィールドを推測で変更しない。
- 認証情報を例外メッセージ、ログ、テストfixture、コミットへ含めない。
- HTTPエラーの診断性を上げる場合、本文の機密性、サイズ、不正JSONを考慮する。
- URLエンコードを変更する場合、二重エンコードを避け、全パラメータを対象に自動テストを用意する。
- タイムアウト、再試行、接続先注入、クローズ方式の変更は挙動・バイナリ互換性を評価する。
- Java 11のソース／ターゲット互換性を維持するか、変更前にサポート方針を確認する。

## 11. NOBY API HTTPエラー対応の設計案

### 11.1 設計対象と前提

本節は、[requirements.md](requirements.md) の「NOBY APIエラーに関する変更要求」に対する設計案である。対象は本リポジトリのJavaクライアントライブラリに限定する。

現行実装で確認できる事項は次のとおりである。

- `NobyClient.exec(String)` はHTTP 200以外でレスポンス本文を読まず、`Exception("HTTP error: <status>")` を送出する。
- `exec` の公開シグネチャは `throws Exception` である。
- ライブラリ本体にロギング依存およびロガーはない。
- 外部接続先は `NobyClient.java` に固定されている。
- `NobyClientTest.java` は `main` メソッドによる手動疎通用で、自動テストではない。
- Alexa応答およびMP3生成・配信を行う実装は本リポジトリにない。

したがって、本設計ではHTTPエラー情報を利用側へ安全に引き渡すところまでを扱う。利用側におけるフォールバック応答、HTTP 500の回避、MP3存在確認の具体設計は、該当実装を確認できる別リポジトリで行う。

### 11.2 推奨案

HTTPエラー専用の `NobyHttpException` を追加し、`NobyClient.exec(String)` から送出する。

専用例外は、少なくとも次の情報を個別に保持する。

- HTTPステータスコード
- NOBY APIから受信したエラーレスポンス本文

例外メッセージは現行と同じ `HTTP error: <status>` 形式を維持し、レスポンス本文を自動的に含めない。本文は明示的なアクセサーを通してのみ利用側が取得できるようにする。これにより、既存の `Exception` 捕捉コードとの互換性を保ちつつ、利用側が400等の原因を調査できる。

`NobyClient.exec(String)` では、HTTPステータスを判定した後、非200の場合だけ本文を文字列として読み取り、専用例外へ渡す。レスポンスは正常・異常を問わず確実にクローズする。HTTP 200の正常JSON変換と、本文に `errors` がある場合の現行動作は今回の変更対象に含めない。

#### 推奨理由

- `exec(String)` の引数、戻り値、`throws Exception` を変更しないため、ソース・バイナリ互換性への影響が小さい。
- 利用側は従来どおり `Exception` で捕捉でき、必要な利用側だけが専用例外を識別できる。
- ステータスと本文を文字列メッセージから解析せず、型付き情報として扱える。
- 本文を `getMessage()` や暗黙の `toString()` に含めないことで、既存の例外ログによる機密情報の偶発的な露出を抑えられる。
- 既存のJersey APIとJDKだけで実装でき、実行時の新規依存を必要としない。
- HTTP 400以外の401、403、429、500系にも同じ契約を適用できる。

#### 本文保持に関する安全策

- 完全な要求URL、要求パラメータ、認証情報は専用例外へ追加しない。
- ライブラリはエラー本文を自動でログ出力しない。
- 本文が空の場合も許容する。
- 本文は最大8,192文字を保持し、超過分を切り詰める。切詰めの有無は `isResponseBodyTruncated()` で公開する。
- NOBY APIのエラー本文に認証情報や個人情報が含まれる可能性があるため、利用側が本文をログへ出す場合のマスキング・長さ制限・保存期間は利用側の責務として明文化する。

### 11.3 代替案

#### 代替案A: 現行の汎用 `Exception` のメッセージへ本文を追加する

利点:

- 変更量が最も少ない。
- 新規例外型を追加せず、既存の例外処理で本文を確認できる。

欠点:

- 既存の例外ログへ本文が自動的に出力され、個人情報・機密情報が漏れる可能性が高い。
- 利用側がステータスや本文を文字列解析する必要がある。
- 例外文言の変更に依存する既存コードへ影響する可能性がある。

安全性と機械判定性の理由から採用を推奨しない。

#### 代替案B: ライブラリ内部でHTTPエラー本文をログ出力し、例外契約は変更しない

利点:

- 利用側コードを変更せず、ライブラリ実行環境のログから調査できる。
- 公開APIへの追加がない。

欠点:

- 現行にないロギング依存またはロギング方式の選定が必要になる。
- ライブラリが利用側のログ方針、マスキング、保存期間を制御できない。
- 本文を必要とする利用側のフォールバック判定には使えない。
- ライブラリ利用者へ予期しないログ出力を追加する。

責務分離と秘密情報保護の理由から採用を推奨しない。

#### 代替案C: `NobyClient.exec(String)` の戻り値を成功・失敗の両方を持つ型へ変更する

利点:

- 正常結果とエラー情報を明示的な戻り値として扱える。
- 例外制御に依存しないAPIを構成できる。

欠点:

- 戻り値型が変わり、既存利用側とのソース・バイナリ互換性を破壊する。
- 全利用側の移行が必要になる。
- 今回の障害対応として変更範囲が大きい。

公開API互換性の制約に反するため採用しない。

#### 代替案D: 既存動作を維持し、利用側だけでHTTP 400を処理する

利点:

- 本ライブラリは変更不要。
- 公開APIへの影響がない。

欠点:

- 現行例外から取得できる情報はステータスだけであり、400の具体的な理由を利用側で確認できない。
- 利用側でNOBY APIのエラー本文を取得する手段がない。

利用側のHTTP 500回避には必要だが、診断性の要求を単独では満たさない。本ライブラリの推奨案と組み合わせる必要がある。

### 11.5 各領域への影響

#### 公開Java API

- `NobyClient` のコンストラクタ、`exec(String)` の引数、戻り値、宣言例外は変更しない。
- HTTPエラー専用例外型の追加は加算的変更とする。
- 既存の `catch (Exception)` は引き続き動作する。
- 例外メッセージ `HTTP error: <status>` は互換性のため維持する。
- 特定の実装クラスとの完全一致を判定している利用側がないかは確認が必要である。

#### 外部HTTP API

- Method、URL、クエリ、Accept、正常レスポンスの解釈は変更しない。
- 非200レスポンス本文を追加で読み取るが、外部APIへ送る要求は変わらない。
- ステータス別の再試行やフォールバックは本ライブラリ内では行わない。

#### 画面

- 本リポジトリに画面はなく、直接影響はない。
- 利用側のエラー表示・Alexa応答は、専用例外から得た情報を内部判定に使える。ただし外部API本文をそのままユーザーへ表示しない。

#### DB

- 本リポジトリにDBはなく、スキーマ、マイグレーション、データ移行への影響はない。

#### エラー

- HTTP 200以外という判定条件は維持する。
- 汎用例外の代わりに、その派生型となる専用例外を送出する。
- HTTP 200本文に `errors` がある場合の現行例外処理は変更しない。
- 通信、TLS、JSON変換等の例外も今回の変更対象外とし、従来どおり伝播させる。

#### ログ

- ライブラリから新規ログを出力しない。
- 既存のロギング依存を追加しない。
- 利用側はステータスをログ記録できるが、本文の記録はマスキング等の運用ルール確定後に限定する。
- 完全な要求URL、認証値、会話文、位置情報は記録しない。

### 11.6 依存関係の方針

実行時依存は追加しない。Jerseyの `Response` 読取機能とJDKの例外機構で要件を満たせる。

自動テストを成立させるため、JUnit 4.13.2をテストスコープで追加する。Java 11とMaven Surefireの自動検出で動作し、追加のテストプラグイン設定を必要としないことを確認済みである。現行には自動テスト基盤がなく、例外契約を回帰検証するために必要な依存である。

HTTPモック専用依存は現時点では追加しない。まず、HTTPステータスと本文から例外を構築する処理を通信処理から分離し、その部分を外部通信なしでテストできる構成を候補とする。接続先注入やモックサーバーは、結合テストの必要性が合意された場合に別途設計する。

### 11.7 テスト方針

#### 自動テスト

- HTTP 400と本文ありで、専用例外がステータスと本文を保持する。
- HTTP 400と空本文を安全に扱う。
- 401、403、404、429、500系でも同じ契約になる。
- 例外メッセージに本文、要求URL、認証情報が含まれない。
- 不正JSON本文をJSONとして解析せず保持できる。
- 正常なHTTP 200の `Result` 変換が従来どおりである。
- HTTP 200の `errors` 応答が従来どおり例外になる。
- レスポンスが正常・異常の両方でクローズされる。

外部URLが固定されているため、実通信を伴わないテストが可能な最小単位へHTTP応答処理を分離する。ただし、公開API化はせず、今回の試験容易性に必要な範囲に限定する。

#### 手動・結合確認

- Java 11環境で `mvn clean verify` が成功する。
- テスト用NOBY APIで、許可を得た上でHTTP 400の実際の本文と専用例外を確認する。
- 利用側システムで、NOBY API失敗時にも有効なフォールバック応答を返し、未処理のHTTP 500にならないことを確認する。
- 音声生成失敗時に、存在しないMP3 URLが返らないことを利用側システムで確認する。
- 正常な会話要求の回帰確認を行う。

本調査環境のJava 21では現行Lombok 1.18.28との互換性問題と考えられるコンパイルエラーが発生しているため、Java 11での検証を正式な判定とする。

### 11.8 移行上の注意

- 専用例外は既存の `Exception` の派生型とし、既存利用側を強制移行させない。
- 詳細情報を利用したい利用側だけが専用例外の判定を追加する。
- 利用側の更新が先行または同時に配布できない場合も、従来の `catch (Exception)` で処理できる状態を維持する。
- 本文をログへ追加する運用は、マスキングと保存方針が決まるまで開始しない。
- ライブラリと利用側の配布順、対象バージョン、JitPack成果物は正式リリース手順の確認後に決定する。

### 11.9 ロールバック上の注意

- DB変更がないためDBロールバックは不要である。
- 問題時は利用側の依存を直前の検証済みライブラリへ戻せるよう、変更前バージョンを記録する。
- 利用側が専用例外型へ直接依存した後にライブラリだけを旧版へ戻すと、クラス不在による互換性問題が生じる。ライブラリと利用側を組として切り戻すか、利用側を従来の `Exception` 捕捉へ戻す手順が必要である。
- 正式な切戻し先は、現行POMの `0.7.2-SNAPSHOT` とGitタグ `v0.7.1` の関係を確認してから決定する。
- ライブラリを切り戻しても、外部NOBY APIの仕様変更や障害自体は復旧しない。

### 11.10 未決事項

- NOBY APIのエラー本文に含まれ得る秘密情報・個人情報と公式スキーマ
- HTTPステータス以外にContent-Type、ヘッダー、リクエスト識別子を保持する必要性
- 利用側のフォールバック文言、セッション継続、再試行、ログ運用
- Alexa応答およびMP3処理を持つ利用側リポジトリの実装確認
- 正式なリリースバージョン、配布順、切戻し先

### 11.11 実装結果

- `NobyHttpException` はHTTPステータス、最大8,192文字の本文、切詰め有無を保持する。
- 本文は生文字列として明示アクセサーから取得できるが、例外メッセージと `toString()` には含まれない。
- 本文読取が失敗した非200応答は、空本文と原因例外を持つ `NobyHttpException` として通知し、元のHTTPステータスを維持する。
